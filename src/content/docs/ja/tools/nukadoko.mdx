nukadoko は、型付きのステップ契約のもとで Gherkin のシナリオを実行し、実行のたびにステップ記録を書き出します。
実装は今や生成されるものになり、それを検査する基準は固定されていなければなりません。
受け入れ基準は、それを決めた人たちの言葉で書かれたままにします。
その文とテスト対象のシステムの間にあるものは、すべて型付きで、実行前に検査され、差分でレビューできます。
ステップ記録はツール自身が測定するので、実行についてのエージェントの説明を信じる必要はありません。
どの実行も、CI がプルリクエストに投稿する Markdown の実行サマリーで終わり、人は差分の中の `.feature` とそのサマリーを並べてレビューします。

## 特徴

- **実行前にわかる誤り。**
  `nuka check` は、すべてのフィーチャーファイルとステップファイルを読み、未定義のステップ、重複したパターン、あいまいなステップ、順序が誤っている `from` のバインディングなどを報告します。
  `nuka check --codes` は、すべての指摘コードを一覧表示します。
- **エージェントが読める語彙。**
  `nuka steps --json` は、各ステップのパターン、説明、`mutates`、`needs` を一覧表示します。
  `nuka describe` は、ステップの契約を、スキーマを JSON Schema の形にして表示します。
- **ステップ記録。**
  `nuka do` は 1 つのステップを単独で実行し、検証済みの結果と、ツールが観測したネットワークの読み書きを含むステップ記録を出力します。
  `nuka run` はシナリオを実行し、同じ記録を残します。
  エクスポートされた `runCommand` を呼ぶステップは、起動した各プロセスのコマンド、作業ディレクトリ、終了コードを `observed.processes` に残します。
- **レビューする人のための実行サマリー。**
  どの `nuka run` も `.nukadoko/records/runs/<run_id>/summary.md` を書き出します。
  そこには、コミット、環境、フィーチャーごとの表、`mutates: false` と宣言したのに書き込みが測定されたステップ、失敗した各シナリオを再実行するコマンドが並びます。
  `$GITHUB_STEP_SUMMARY` が設定されていればそこに追記し、`--summary <path>` を渡すと、CI のステップがプルリクエストのコメントとして投稿できる写しを書き出します。
- **理由がわかる失敗。**
  ステップが失敗すると、`nuka run` はそのエラーの 1 行目とステップ記録のパスを stderr に出力し、サマリーの後には失敗した各シナリオについて `rerun  nuka run <feature>:<line>` の行を出力します。
  `--quiet` を付けても、これらの行は残ります。
- **既存のスイートの入口。**
  import を 1 つ `@cucumber/cucumber` から `nukadoko/compat` に替えると、cucumber-js のスイートは動き続け、nukadoko がそのステップを記録し始めます。
  その後、各ステップを個別に `defineStep` へ移せます。

## エージェントでの使い方

エージェントは、人の手を借りずにループ全体を回せます。

1. `nuka steps --json` で語彙を調べます。
2. `nuka describe` で契約を読みます。
3. `nuka do` で 1 つのステップを実行し、ステップ記録を読んで、次の呼び出しを選びます。
4. 語彙に操作が足りなければ、`nuka scaffold <name> --pattern "<line>"`(Then のステップには `--then`)でステップを追加して実装し、`nuka do` で単独で動かします。
   検証するだけのステップは `returns` を省けます。
   一時ディレクトリが必要なステップは組み込みの `scratch` フィクスチャを使い、そのディレクトリはシナリオの終了時に削除されます。
5. フィーチャーを書き、`nuka check <feature>` を通し、green になるまで `nuka run <feature>` を実行します。
   失敗したときは、失敗したステップの記録を読みます。
6. フィーチャーとその実行サマリーを渡します。
   人はプルリクエストで両方を読み、それを承認します。

`nuka check` は、毎回の実行の前に通す静的なゲートです。
`nuka tend` はときどき実行するもので、説明のないスキーマのフィールドのように、壊れてはいないが傷みつつあるものを報告します。
パッケージには 2 つのスキルが含まれています。
`acceptance` はチケットの受け入れ基準から人が承認できるプルリクエストまでを進め、`migration` は cucumber-js のスイートを nukadoko に移行します。

## はじめかた

nukadoko には Node 20 以降が必要です。

```sh
npm install -D nukadoko
npx nuka init
npx nuka steps
```

`nuka init` は、CLI や API のプロジェクトを前提に準備をします。
`nukadoko.config.ts` と `features/steps/` を書き出し、`.gitignore` に `.nukadoko/` を追加し、`nuka check && nuka run features` を実行する `test:scenarios` スクリプトを追加します。
以後、人も CI も `npm run test:scenarios` の 1 つだけを実行すれば済みます。
Allure と cucumber-messages の出力は、設定にそのキーがあるときだけ有効になり、`nuka init --allure` で Allure を有効にできます。
`gh skill install meganemura/nukadoko --all` で、2 つのスキルをインストールします。
