nukadoko は、型付きのステップ契約のもとで Gherkin のシナリオを実行し、実行のたびにステップ記録を書き出します。
今は実装が生成される時代で、それを検査する基準は動かないままでなければなりません。
受け入れ基準は、それを決めた人たちの言葉のままです。
その文と、テスト対象のシステムの間にあるものは、すべて型付きで、実行前に検査され、差分でレビューできます。
ステップ記録はツール自身が測定するので、実行についてのエージェントの説明を信じる必要はありません。

## 特徴

- **実行前にわかる誤り。**
  `nuka check` は、すべてのフィーチャーファイルとステップファイルを読み、未定義のステップ、重複したパターン、あいまいなステップ、順序の誤った `from` の結び付けなどを報告します。
  `nuka check --codes` は、すべての指摘コードを一覧します。
- **エージェントが読める語彙。**
  `nuka steps --json` は、各ステップのパターン、説明、`mutates`、`needs` を一覧します。
  `nuka describe` は、ステップの契約を、スキーマを JSON Schema にして示します。
- **ステップ記録。**
  `nuka do` は 1 つのステップを単独で実行し、検証済みの結果と、ツールが観測したネットワークの読み書きを含むステップ記録を出力します。
  `nuka run` はシナリオを実行し、同じ記録を残します。
- **承認。**
  `nuka accept` は、1 回の成功した実行を、フィーチャーの隣の Markdown の記録として固定します。
  その `Declared vs observed` の節は、`mutates: false` と宣言しながら書き込みが測定されたステップを並べます。
- **配線のいらない報告。**
  どの実行も、設定なしで Allure の結果と cucumber-messages のストリームを書き出します。
  Allure の各ステップには、検証済みの結果、そのステップ自身のトレース、待ちと Playwright の呼び出しのタイムラインが付きます。
- **既存のスイートの入口。**
  import を 1 つ `@cucumber/cucumber` から `nukadoko/compat` に替えると、cucumber-js のスイートは動き続け、nukadoko がそのステップを記録し始めます。
  その後、各ステップを 1 つずつ `defineStep` に移せます。

## エージェントでの使い方

エージェントは、人の手を借りずに一巡を終えられます。

1. `nuka steps --json` で語彙を調べます。
2. `nuka describe` で契約を読みます。
3. `nuka do` で 1 つのステップを実行し、ステップ記録を読んで、次の呼び出しを選びます。
4. 語彙に操作が足りなければ、`nuka scaffold <name>` でステップを足して実装します。
   その後、人がプルリクエストをレビューします。

`nuka check` は、毎回の実行の前に通す静的な関門です。
`nuka tend` はときどき実行するもので、説明のないスキーマのフィールドのような、壊れてはいないが傷みつつあるものを報告します。
パッケージには 2 つのスキルが入っています。
`acceptance` はチケットの受け入れ基準をコミット済みの記録まで運び、`migration` は cucumber-js のスイートを移します。

## はじめかた

nukadoko には Node 20 以降が必要です。

```sh
npm install -D nukadoko
npx nuka init
npx nuka steps
npx nuka check
```

`nuka init` は `nukadoko.config.ts` と `.gitignore` のエントリを書き出します。
`gh skill install meganemura/nukadoko --all` で 2 つのスキルを入れられます。
