solarsql は、Cloudflare の D1 と Durable Objects 上の SQLite のための、型付きの SQL レイヤーです。
モジュールを 1 つずつ読むコーディングエージェントと、その作業を確認する人のために書かれています。
SQL は文字列リテラルで書き、ビルド時に本物のエンジンへ各文の戻り値を問い合わせて、その型を書き出します。
SQL を変えてビルドしていないと、tsc がその SQL の文字列にエラーを出します。
1.0 までは、マイナーバージョンで API が変わることがあります。

## 特徴

- **エンジンから取る型。**
  `npx solarsql build` は、すべてのクエリを node:sqlite で実行し、`solarsql.generated.ts` を書き出します。
  失敗した文は `at:` の行つきで返り、`no such column` のメッセージにはそのテーブルの列が並びます。
- **コマンドは 1 つのトランザクション。**
  コマンドは、文と `assert(...)` による検査を並べた `plan` で、D1 の 1 つのバッチ、または Durable Object の 1 つのトランザクションとして動きます。
  `db.run` は `{ ok: true, rows }` か、`kind` が `"assert"` や `"unique"` などの失敗の値を返します。
- **テーブルを持つモジュール。**
  モジュールは `module.ts`、`public.ts`、`solarsql.generated.ts` の 3 つのファイルです。
  ほかのモジュールのテーブルに書き込む文はビルドが拒み、ほかのモジュールは `public.ts` だけを通して import します。
- **スキーマから作るマイグレーション。**
  `npx solarsql migration <name>` は、`migrations/NNNN_<name>.sql` と、Durable Object 用の `migrations/index.ts` を書き出します。
  ファイルがスキーマを再現しなくなると、ビルドが新しいマイグレーションを求めます。
- **実データでのリハーサル。**
  デプロイの前に、実データのスナップショットに対してマイグレーションをリハーサルできます。
  失ったり変わったりした行があると、`checks.json` でその変化を宣言していない限り、リハーサルは失敗します。
- **3 つの実行先で同じ API。**
  `d1(env.DB)`、`durable(ctx.storage)`、`node(db)` は、同じ `db.all`、`db.first`、`db.run`、`db.batch` を返します。
  モジュールのテストは node:sqlite で動きます。

既存の SQLite スキーマがあるプロジェクトは、モジュールの規則なしで DDL を受け付けるスキーマだけのクエリ生成から始められます。

## エージェントでの使い方

使い方の文書はスキルとしてパッケージに入っています。
プロジェクトの AGENTS.md から `node_modules/solarsql/skills/solarsql/SKILL.md` を指してください。

1. `module.ts` のテーブル、クエリ、コマンドを編集します。
2. `npx solarsql build` を実行します。
   各メッセージに直し方が書いてあります。
3. ビルドがマイグレーションの文を表示したら、`npx solarsql migration <name>` を実行します。
4. `node --test` でモジュールのテストを実行します。

## はじめかた

```sh
npm install solarsql
npm install --save-dev typescript @types/node
npx solarsql init orders
node --test
```

`init` は、`solarsql.config.ts` と、仮のテーブル、クエリのカタログ、2 つのコマンド、node:sqlite 上のテストを持つモジュール `modules/orders/` を書き出します。
続けて最初のビルドを実行し、`migrations/0001_initial.sql` を書き出します。
