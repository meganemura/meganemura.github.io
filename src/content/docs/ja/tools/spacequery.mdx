spacequery は、開発者のマシンの現在の状態を、コーディングエージェントに 1 つの見え方で渡します。
エージェントは、編集する、サーバーを起動する、プルリクエストを開く、古い作業を引き継ぐといった前に、マシンとリポジトリを誰が何で使っているかを知る必要があります。
git、gh、プロセスのツール、端末のセッションは、それぞれその一部しか見せません。
spacequery は、プロバイダーと呼ぶそれらの情報源を観測し、その行を新しいインメモリの SQLite データベースで結合して、結果を表示して終了します。
情報源を読むだけで、変えることはありません。

## 特徴

- **リポジトリごとの報告。**
  `spacequery here` は、そのリポジトリにいるほかのエージェント、git の状態、リンクされたワークツリー、ブランチのプルリクエスト、待ち受け中のポート、ローカルのプロセス、Docker のコンテナ、mise のツールなどの節を表示します。
- **ツールをまたぐ問い。**
  spacequery はリポジトリのルートで行を結合するので、`agents-in-dirty-repos`、`failing-checks-with-agents`、`idle-worktrees`、`servers-with-agents` はそれぞれ 1 つの名前付きクエリです。
- **作業前の関門。**
  エージェントを一覧するクエリは、呼び出したエージェント自身を除きます。
  `spacequery here --expect-empty --strict` は、ほかのエージェントがリポジトリにいるときや、答えなかったプロバイダーがあるときに失敗し、`spacequery watch in-dir --until empty` はリポジトリが空くまで待ちます。
- **見える欠け。**
  既定の出力は JSON で、`providers` フィールドが、実行した各プロバイダーの `source`、`ok`、`observed_at`、`ms`、`error` を示します。
  失敗したプロバイダーのテーブルは空になるので、その横の空の行は「ない」ではなく「わからない」を意味します。
  `spacequery doctor` は、組み込みのどのプロバイダーが答えるかを確かめます。
- **必要なプロバイダーだけ。**
  クエリは、読むテーブルのプロバイダーだけを読み込むので、`tools-in-dir` は GitHub を呼びません。
  呼び出しのたびに空のデータベースから始めるので、古くなるキャッシュはありません。
- **端末のブラウザー。**
  `spacequery ui` は、テーブルとクエリを列と SQL つきで表示し、`r` を押すと行を取得します。
  `--tsv` は、人が読むための簡潔な表を出力します。

## エージェントでの使い方

作業の流れは spacequery のスキルにあり、`gh skill install` でエージェントのホストごとに入れます。

1. リポジトリで作業を始める前に、エージェントは `spacequery here` を実行します。
2. `section_status` を読み、各節の元になったプロバイダーが答えたかを確かめます。
3. 行を見て、より安全な次の行動を選びます。
   ほかのエージェントが作業中なら `spacequery watch in-dir --until empty` で待ち、空いているワークツリーを使い、ローカルのサーバーが使っているポートを避け、マージを頼む前に失敗しているチェックを読みます。

## はじめかた

spacequery には、Node 24.10 以降と、観測するツール (`git`、`gh`、`herdr`、`docker`、`lsof` など) が `PATH` 上に必要です。

```sh
npm install -g spacequery
spacequery here
spacequery doctor
gh skill install meganemura/spacequery spacequery --scope user --agent claude-code
```
